# 工作流编排与实例展示 PRD

## 0. 当前达成程度与本期边界

> 实施状态（2026-08-31）：阶段 1 与阶段 2 的前端实现已完成。React Flow 模板画布、实例画布、节点属性面板、并行进度、任务操作状态和 XState 状态机均已接入；真实多人任务与完整打回记录仍受当前后端字段限制。

### 0.1 目标

本需求分为两个阶段：

- **阶段 1：工作流模板编辑器升级**。使用 React Flow 替换当前按列表/阶段编辑的交互，但保留现有后端接口和 `sort + parallelSort` 数据模型。
- **阶段 2：工作流实例展示升级**。在项目任务流中展示任务状态、执行人、并行进度、当前可操作任务和打回状态。

### 0.2 本期编辑器可以完成到什么程度

本期编辑器可以完成：

- 在画布中展示工作流节点。
- 从节点库添加预定义任务。
- 拖拽节点调整执行顺序。
- 将节点拖入同一并行组。
- 展示线性阶段和并行阶段的视觉关系。
- 选中节点并在属性面板编辑名称、说明等前端已有字段。
- 删除节点。
- 保存时将画布数据转换为后端当前要求的 `sort + parallelSort`。
- 加载已有模板并还原为画布。
- 保存前进行基本流程校验。

### 0.3 本期编辑器不能完成的能力

由于当前后端只支持按 `sort` 分组的线性流程，本期不实现：

- 任意节点之间的持久化连接。
- 审核通过/失败形成不同分支。
- 任意条件分支。
- 任意循环边。
- 子流程和嵌套流程。
- 运行时动态生成节点。
- 复杂的节点变量和表达式。
- 由前端单独决定工作流状态流转。

画布中的连接线在本期主要用于视觉表达和交互辅助，最终保存结果仍以阶段顺序和并行关系为准。

### 0.4 阶段 2 可以完成到什么程度

阶段 2 可以完成：

- 以 React Flow 展示工作流实例。
- 显示节点当前状态。
- 显示任务接取人。
- 显示当前用户可执行的操作。
- 显示并行组的完成进度。
- 显示被打回的节点和打回意见。
- 显示当前正在执行的阶段。
- 使用状态机统一管理前端按钮权限、请求中状态和刷新流程。

阶段 2 仍不改变后端任务状态定义。后端当前的 `PENDING`、`CLAIMED`、`COMPLETED` 以及 reject 接口仍是权威来源。

## 1. 背景与问题

当前工作流模板编辑器以阶段列表为主要交互，能够表达固定顺序和并行步骤，但不够直观：

- 用户难以快速理解流程整体结构。
- 并行节点与普通节点的关系不够明显。
- 节点顺序调整和并行关系调整不够自然。
- 工作流实例页面更偏任务列表，不能直观表达流程进度。
- 状态判断分散在多个组件中，接取、提交、打回和刷新逻辑容易重复。

汉化组常见流程包括：

```text
创建任务 → 前期调研 → 翻译 → 翻译审核 → 嵌字 → 嵌字审核 → 发布
```

也可能存在：

```text
翻译 → 翻译审核
           ├─ 通过 → 嵌字
           └─ 失败 → 翻译
```

本期先解决可视化编辑和实例状态展示，未来再升级为真正的节点边工作流引擎。

## 2. 产品目标

### 2.1 主要目标

1. 让组长可以用画布直观创建和调整工作流模板。
2. 保持与现有后端接口兼容，降低改造风险。
3. 让组员和组长可以快速看懂项目当前进度。
4. 让并行任务的完成条件和当前进度清晰可见。
5. 让接取、提交、打回等操作具有明确的状态反馈。
6. 为未来的 DAG 工作流模型保留扩展空间。

### 2.2 非目标

本期不建设通用 BPM 平台，不实现：

- 多租户管理端。
- 复杂权限矩阵。
- 自动化脚本节点。
- 外部系统触发器。
- 通知编排。
- 工作流变量表达式。
- 工作流版本发布体系。
- 移动端专项交互。

## 3. 用户角色与权限

### 3.1 组织管理员/组长

- 创建、查看、编辑自己的工作流模板。
- 创建、查询、启用和禁用组织原子任务；原子任务创建后不可编辑或删除。
- 在创建项目时选择可用模板。
- 查看项目完整工作流实例。
- 接取规则允许时处理任务。
- 对符合权限的任务执行打回。

### 3.2 普通组员

- 查看项目工作流实例。
- 查看节点状态和执行人。
- 接取当前可接取任务。
- 提交本人已接取的任务。
- 查看自己参与的任务。
- 不可进入原子任务管理和工作流模板编排页面。

### 3.3 权限原则

- 前端只负责展示和预校验，不能代替后端鉴权。
- 所有接取、提交、打回操作必须以 API 成功结果为准。
- API 失败时恢复页面状态并提示原因。

## 4. 技术选型

### 4.1 核心技术

- **React Flow**：使用 `@xyflow/react`，负责画布、节点、边、拖拽、缩放、选择和连接交互。官方支持自定义节点和多个 Handle。[React Flow 官方文档](https://reactflow.dev/learn/customization/custom-nodes)
- **XState v5**：使用 `xstate` 和 `@xstate/react`，负责前端业务状态、任务状态转换、并行组状态聚合、API 操作中状态和页面刷新流程。[XState 官方文档](https://stately.ai/docs/xstate)
- **shadcn/ui**：负责按钮、表单、抽屉、面板、Badge、Tooltip、Dialog 等基础 UI。
- **react-hook-form + zod**：负责节点属性表单和保存前校验。
- **Tailwind CSS**：遵循项目现有样式规范，不新增独立 CSS 文件。

### 4.2 自动布局

第一期优先使用现有位置或简单阶段布局，不强制引入自动布局库。

后续如果节点数量和分支复杂度增加：

- 首选 `elkjs`：适合有向、分层、带端口的图布局。[ELK.js 官方仓库](https://github.com/kieler/elkjs)
- 备选 `@dagrejs/dagre`：接入简单，适合基础的线性或分层流程。

### 4.3 状态机使用原则

- XState 只描述前端允许的状态和事件，不替代后端持久化。
- 后端返回的数据是状态初始化和刷新依据。
- API 请求期间进入独立的操作中状态，避免重复提交。
- 状态机不负责保存 React Flow 的全部节点位置数据。
- 模板编辑状态机与任务实例状态机分离。

## 5. 核心概念与数据模型

### 5.1 工作流模板

模板定义可复用的流程结构，不包含具体项目中的执行状态。

当前后端模型：

```ts
interface WorkshopTaskTemplateNodeCreateDTO {
  baseTaskId: string;
  customName?: string;
  sort: number;
  parallelSort?: number;
}
```

### 5.2 工作流实例

项目绑定模板后生成自己的实例。模板后续修改不得影响已实例化的项目。

当前实例节点包含：

```ts
interface ItemTaskNodeVO {
  id: string;
  baseTaskId: string;
  name: string;
  metaSchema?: string;
  sort: number;
  parallelSort: number;
  taskInstanceId?: string | null;
  taskStatus?: "PENDING" | "CLAIMED" | "COMPLETED" | null;
}
```

### 5.3 前端派生状态

后端没有 `LOCKED`，前端根据阶段完成情况派生：

```text
LOCKED：没有 taskInstanceId，且前置阶段未完成
PENDING：可接取
CLAIMED：已接取，等待提交
COMPLETED：已完成
REJECTED：由 reject 信息派生，不直接作为当前后端状态提交
```

## 6. 阶段 1：工作流模板编辑器

### 6.1 页面布局

```text
┌─────────────────────────────────────────────┐
│ 返回  流程名称                 保存          │
├──────────────┬──────────────────┬───────────┤
│ 节点库        │ React Flow 画布   │ 属性面板   │
│              │                  │           │
│ 翻译         │   节点 → 节点      │ 节点名称   │
│ 审核         │       ↘           │ 任务说明   │
│ 嵌字         │      并行组        │ 删除节点   │
└──────────────┴──────────────────┴───────────┘
```

桌面端使用三栏布局。较窄屏幕下属性面板改为抽屉，节点库改为可展开区域。

### 6.2 节点库

节点库展示后端返回的基础任务，不在前端写死任务类型。

每个可添加任务展示：

- 图标。
- 任务名称。
- 任务说明摘要。
- 是否已被禁用。

拖拽到画布或点击添加均可创建节点。

### 6.3 节点表现

节点至少展示：

- 任务图标。
- 自定义名称或基础任务名称。
- 所属阶段序号。
- 并行标记。
- 节点配置异常提示。

节点被选中时使用品牌色边框或高亮，不使用大面积渐变文字。

### 6.4 拖拽规则

- 拖动节点到另一个阶段区域：调整 `sort`。
- 拖动节点到同一阶段：加入并行组。
- 同一阶段中的节点可调整显示顺序，重新计算 `parallelSort`。
- 删除节点后重新整理阶段序号。
- 节点位置只作为画布展示信息，不提交给当前后端。
- 保存前统一执行 `normalizeNodes`，避免序号出现空洞或重复。

### 6.5 属性面板

当前阶段只编辑后端已有能力：

- 自定义节点名称。
- 查看基础任务名称。
- 查看任务说明。
- 查看基础任务图标。
- 查看当前阶段和并行序号。
- 删除节点。

暂不在属性面板承诺下列功能，除非后端接口明确支持：

- 自定义分支条件。
- 审核目标节点。
- 节点负责人规则。
- 多人完成策略。
- 自动化动作。

### 6.6 保存流程

保存流程前执行：

1. 流程名称非空。
2. 至少存在一个节点。
3. 节点的 `baseTaskId` 有效。
4. 节点没有重复的本地 ID。
5. 阶段序号连续。
6. 并行序号从 1 开始连续。
7. 所有禁用基础任务给出明确提示。

保存时转换为：

```ts
WorkshopTaskTemplateCreateDTO {
  name,
  description,
  nodes: normalizeNodes(nodes).map(toCreateNode)
}
```

### 6.7 编辑器状态机

建议状态：

```text
idle
 ├── editing
 ├── validating
 ├── saving
 ├── saved
 └── error
```

事件：

```text
NODE_ADDED
NODE_UPDATED
NODE_MOVED
NODE_DELETED
SAVE
SAVE_SUCCESS
SAVE_FAILURE
RESET
```

保存按钮在 `validating` 和 `saving` 期间禁用。保存成功后清除脏状态并返回模板列表，或根据页面现有交互保留在当前页。

## 7. 阶段 2：工作流实例展示

### 7.1 展示目标

实例页面要让用户在进入页面后快速回答：

- 当前流程走到哪一步？
- 哪些任务已经完成？
- 哪些任务可以接取？
- 谁正在处理？
- 并行任务完成了多少？
- 哪个任务被打回以及原因是什么？

### 7.2 实例画布

实例画布默认按阶段从左到右或从上到下展示：

- 已完成节点：低饱和绿色。
- 当前可接取节点：品牌粉色高亮。
- 已接取节点：暖色高亮，并展示执行人。
- 已锁定节点：灰色弱化。
- 被打回节点：红色标识，并展示打回原因入口。
- 并行组：使用容器背景和 `已完成数量 / 总数量` 标识。

不要求通过动画表达全部状态变化，动画只用于当前节点、正在执行的边或刷新反馈。

### 7.3 节点卡片

节点卡片展示：

- 节点名称。
- 状态 Badge。
- 执行人头像和昵称。
- 并行进度。
- 当前用户是否负责。
- 可执行操作。
- 打回原因摘要。

### 7.4 操作规则

| 状态      | 当前用户                 | 操作           |
| --------- | ------------------------ | -------------- |
| PENDING   | 任意有权限成员           | 接取           |
| CLAIMED   | 当前负责人               | 提交           |
| CLAIMED   | 非当前负责人             | 查看处理中状态 |
| COMPLETED | 任意                     | 查看详情       |
| 被打回    | 原负责人或符合权限的成员 | 重新处理       |

实际按钮是否展示以 API 返回和后端权限结果为准。

### 7.5 并行进度

对同一 `sort` 的节点进行聚合：

```text
总任务数 = 当前阶段节点数
完成数 = status === COMPLETED 的节点数
当前阶段完成 = 完成数 === 总任务数
```

阶段未全部完成时，下一阶段保持锁定。

如果后端返回的节点实例数量与模板节点数量不一致，前端展示实际返回数据，并提示数据异常，不自行补造任务实例。

### 7.6 打回展示

打回信息至少包括：

- 被打回节点。
- 打回人，如接口提供。
- 打回时间，如接口提供。
- 打回意见。
- 当前是否需要重新接取或继续处理。

打回不由前端直接改变任务状态。调用 reject API 成功后重新拉取工作流实例。

## 8. XState 状态设计

### 8.1 任务状态机

当前后端兼容的最小状态：

```text
PENDING --CLAIM--> CLAIMED
CLAIMED --SUBMIT--> COMPLETED
CLAIMED --REJECT--> CLAIMED
```

`REJECTED` 作为页面派生状态展示，不作为当前后端任务状态直接提交。

### 8.2 页面操作状态机

```text
ready
 ├── loading
 ├── loaded
 ├── claiming
 ├── submitting
 ├── rejecting
 ├── refreshing
 └── error
```

规则：

- 同一个任务的操作请求不能并发重复发送。
- 请求成功后刷新实例数据。
- 请求失败后恢复到请求前的可操作状态。
- 页面卸载后取消或忽略过期请求结果。

### 8.3 是否需要一个完整的动态工作流状态机

本期不根据 React Flow 画布动态生成完整 XState machine。原因是当前后端并不保存真实边关系，动态生成会造成前端模型和后端模型不一致。

后续后端升级为 `nodes + edges + execution` 后，再考虑按模板动态生成状态机。

## 9. API 与现有代码兼容

本期优先复用现有接口：

- 工作流模板创建。
- 工作流模板列表。
- 工作流模板编辑。
- 基础任务选项。
- 工作流实例查询。
- 接取任务。
- 提交任务。
- 打回任务。

前端不新增无法由当前 Swagger 支持的字段，不伪造接口，不把 React Flow 的 `position`、`edges` 写入现有 DTO。

建议新增的前端内部类型只用于画布适配：

```ts
interface WorkflowCanvasNodeData {
  baseTaskId: string;
  label: string;
  sort: number;
  parallelSort: number;
  status?: TaskInstanceStatus | null;
}
```

## 10. 错误与异常处理

- 基础任务加载失败：画布不可添加节点，保留已加载节点并显示重试。
- 模板加载失败：显示错误页和重试操作。
- 保存失败：保留用户画布，不清除脏状态。
- 节点配置非法：保存前在节点和属性面板显示错误。
- 接取冲突：提示“该任务已被其他成员接取”，然后刷新实例。
- 提交失败：保留表单内容，允许重试。
- 打回失败：保留打回意见，允许重试。
- 实例数据不完整：显示可理解的异常提示，不让页面崩溃。

## 11. 验收标准

### 11.1 模板编辑器

- 能加载已有模板并在 React Flow 画布中展示。
- 能从基础任务列表添加节点。
- 能删除节点。
- 能拖动节点调整阶段顺序。
- 能将多个节点放入同一并行阶段。
- 能编辑自定义名称。
- 保存后重新加载，节点阶段和并行顺序保持一致。
- 保存失败时用户编辑内容不丢失。
- 空流程和非法节点不能保存。
- 不修改现有后端 DTO 的语义。

### 11.2 工作流实例

- 能展示锁定、待接取、已接取、已完成状态。
- 能展示当前执行人。
- 能展示并行组进度。
- 能高亮当前用户可执行任务。
- 能发起接取、提交、打回操作。
- 操作成功后状态和画布同步刷新。
- 操作失败后给出反馈并恢复可操作状态。
- 打回原因能够被查看。

### 11.3 工程质量

- 遵循项目 TypeScript、React、Tailwind 和 shadcn/ui 规范。
- 新增依赖统一使用 `vp add`。
- 修改完成后执行 `vp check`。
- 关键状态转换和数据转换应有单元测试。
- 不在组件中重复实现同一套状态判断。

## 12. 后续升级方向

当阶段 1～2 稳定后，再评估后端是否升级为：

```text
WorkflowTemplate
  ├── nodes
  └── edges

WorkflowInstance
  ├── node executions
  ├── edge transitions
  └── execution history
```

届时可以支持：

- 审核通过/驳回分支。
- 任意前置节点回退。
- 多前置节点汇聚。
- 多种并行完成策略。
- 同一内容拆分为多个任务实例。
- 工作流版本。
- 流程运行日志。
- 根据模板动态生成更完整的 XState 状态机。

## 13. 待业务确认的问题

以下问题不影响阶段 1 开始，但会影响阶段 2 和后续后端升级：

1. “多人接取”是多人共同处理同一份内容，还是每个人处理不同内容单元？
2. 并行组是否始终要求全部任务完成？
3. 一个并行任务被打回时，是只回退该任务，还是整个并行组回退？
4. 审核失败是否固定回到指定前置节点？
5. 是否允许跳过中间节点打回更早节点？
6. 打回后是否保留每次提交和审核记录？
7. 提交任务后是否直接视为完成，还是进入独立的待审核状态？
8. 模板被项目使用后是否允许编辑，还是需要复制新模板？
9. 是否需要项目创建后动态调整并行任务数量？
10. 一个项目未来是否可能绑定多个工作流？

这些问题在后端支持真正 DAG 之前，可以继续使用当前 MVP 的线性并行规则；一旦升级节点边模型，则应在后端状态机设计前确定。
