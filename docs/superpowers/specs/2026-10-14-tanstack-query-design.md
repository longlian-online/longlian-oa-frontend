# 接口数据管理全量迁移至 TanStack Query 规格说明

- 日期：2026-10-14
- 分支：`refactor/tanstack-query_2026-10-14`
- 状态：代码已迁移，自动验证已执行；真实后端验收状态见验收记录
- 适用范围：本仓库现有用户端、组织管理端和系统管理端的实际接口调用

## 1. 为什么要做

目前底层已经通过 `src/api/request.ts` 统一使用原生 fetch，处理地址、Token、组织请求头、响应解析、业务异常和登录过期。问题主要在调用层：页面和 Hook 各自使用 useEffect、useState、加载函数和 try/catch 管理服务端数据。

这种方式需要每个调用点独立处理首次加载、刷新、失败和操作后重新加载；多个组件读取同一资源时难以统一复用；参数快速变化时需要自行防止旧结果覆盖新结果；跨页面操作后容易遗漏关联资源刷新。`src/api/user.ts` 已存在手写缓存，`useOrganizationSwitcher` 另有请求序号、单飞等待和会话检查，说明共享数据和竞态处理已经产生实际维护成本。

本次引入 TanStack Query v5，统一服务端数据生命周期。预期收益是减少重复请求状态代码、统一缓存复用与失效、让分页和筛选与数据身份绑定，并使组织和账号隔离可以集中验证。收益以行为测试和迁移清单验证，不承诺未经测量的请求数量或性能提升。

这次引入对应 MVP 文档所说的明确共享状态痛点，不扩展产品功能范围，也不把本地交互状态全部迁入数据缓存。

## 2. 目标与完成定义

1. 现有 React 调用方的服务端读取由 Query 管理，用户主动执行的操作由 Mutation 管理。
2. 现有 API 地址、方法、DTO、响应类型和业务规则保持兼容。
3. 调用方可直接使用 data、error、isLoading、isFetching、refetch 或 mutateAsync、isPending 等标准结果。
4. 不再为同一请求维护第二份页面数据、loading、saving 和请求竞态机制。
5. 缓存隔离、操作后刷新、取消、错误提示和未保存草稿保护有明确规则与测试证据。
6. 全量迁移指仓库当前真实存在的调用点全部完成，并不要求将未使用的 API 导出包装为 Hook。
7. 最终交付必须包含调用点清单、缓存失效映射和验收结果；不能只迁移工作流页面就宣称完成。

## 3. 架构选择

采用“业务 Hook / Query options → 现有 API 函数 → request.ts → fetch”。

- `src/main.tsx` 接入稳定的 QueryClientProvider，不能在组件每次渲染时重建 QueryClient。
- `src/lib/queryClient.ts` 定义 QueryClient、默认策略和缓存生命周期协调。
- `src/lib/queryKeys.ts` 定义结构化 key 工厂。
- `src/hooks/queries/` 提供作用域适配器 useApiQuery/useApiMutation，业务调用方声明资源 key、接口函数和失效目标；现有业务 Hook 保留兼容入口。
- `src/api/*` 继续提供明确类型的 Promise 接口，供 Query、测试和非组件调用使用。
- `request.ts` 保留 fetch 与现有协议处理，支持读取请求传入 AbortSignal，并保留取消异常。
- 不增加另一个通用 useFetch 框架，不通过包装隐藏 queryKey 和错误策略，也不把 Hook 放进 request()。
- 业务 Hook 尽量直接返回 TanStack Query 标准结果；兼容现有公共 Hook 的命名时只派生字段，不复制状态。

相比自行增强 fetch，此方案额外解决 React 订阅、缓存和失效；相比只迁移少数页面，全量迁移避免长期维护两套服务端状态模式。

## 5. 缓存身份和会话生命周期

### 5.1 key 结构

key 必须包含影响结果的端、会话身份、组织、资源 ID、分页和筛选参数。建议结构：

- 组织读取：`['app', sessionScope, 'org', orgId, resource, 'list', params]`
- 组织详情：`['app', sessionScope, 'org', orgId, resource, 'detail', id]`
- 账号读取：`['app', sessionScope, 'account', orgId, resource]`
- 系统管理：`['admin', adminSessionScope, resource, params]`
- 未登录公开读取：`['public', appSessionScope, adminSessionScope, resource, params]`

sessionScope 是非敏感会话代号，与登录生命周期绑定，同一账号重新登录也获得新作用域。Token 不出现在 key、日志或 Devtools 中。请求仅在身份和所需组织存在时启用，不能用空组织 key 发出组织业务请求。

### 5.2 切换与清理

- 会话与组织上下文必须可订阅，不能假设 localStorage 写入会触发 React 更新。
- 普通端与系统管理端可分别退出；仅清理对应作用域，不误伤另一端会话。
- 退出或登录过期：先停止旧作用域的消费并取消请求，清除对应 Query 和 Mutation 结果，防止敏感数据保留；退出请求所需凭证在发出前正确捕获。
- 登录、账号变化：新会话作用域不复用旧缓存，包括同一账号重新登录。
- 切换组织：成功后生效新组织上下文，取消并清理旧组织相关活动缓存。当前使用整页跳转的行为可以保留；清理机制仍必须独立存在，不能仅依赖页面刷新。
- 旧会话 Mutation 完成时不得修改新会话的组织、缓存、导航或表单。
- Query key 与实际发送的组织头和身份必须一致；延迟执行、重试或切换期间不能让旧 key 读取新组织数据。实现可固定请求上下文，或在执行前检查上下文并取消过期请求。
- `user.ts` 原有缓存、缓存失效函数及单飞逻辑迁出或删除；共享来源统一为 Query 缓存。
- 不启用 localStorage/IndexedDB 的 Query 持久化，不引入离线写入队列。

## 6. 加载、缓存和刷新策略

- Query 默认 staleTime 为 30 秒，类型和普通选项为 5 分钟；默认 gcTime 为 5 分钟。
- 任务流程、实例状态和任务详情 staleTime 为 0，重新进入或窗口重新聚焦时允许刷新，操作成功后立即失效。
- 窗口重新聚焦、重连只刷新启用且过期的查询，不启用默认轮询。
- 携带签名附件地址的任务详情不能因通用缓存策略复用已过期链接；读取/展示时依据 expiresAt 判断有效性，过期重新获取，仍失败则展示不可用状态，不请求失效链接。
- 同 key 的并发读取复用同一请求；没有读取需求的 Mutation 不做请求去重假设。
- 首次加载用 isLoading/isPending 按语义判断；禁用且没有数据时不得一直显示正在请求。
- 后台刷新保留现有数据，使用 isFetching/isRefetching 显示局部状态。刷新失败不能把已有列表清空或显示成功的空状态。
- 同身份、同组织、同筛选下的分页可以使用上一页占位数据，并标识 isPlaceholderData；账号、组织或筛选变化不沿用旧占位数据。
- 页面刷新按钮调用 refetch；跨页面刷新使用 queryClient 的失效或精确更新能力。

## 7. Mutation 与关联失效

Mutation 默认 retry 为 0。提交中禁用相关按钮；对原有领取、切换组织等同步防重复锁保持等价保障，不能假设 useMutation 自动串行化请求。业务成功与缓存刷新失败分别处理，不能因为后续读取失败提示“创建失败”并诱导重复提交。

不引入新的乐观更新，任务状态以服务端重新读取结果为准。成功回调负责业务域内的失效，页面仅处理关闭弹窗、清理草稿和导航。

| 操作                         | 必须刷新或精确更新的资源                                                  |
| ---------------------------- | ------------------------------------------------------------------------- |
| 创建/修改模板、模板状态变更  | 对应模板列表、已缓存详情、模板选项                                        |
| 基础任务创建/修改/状态变更   | 基础任务列表及选项、受影响模板读取                                        |
| 企划创建/修改/状态变更       | 企划列表、详情、组织管理项目列表、相关工坊/广场读取                       |
| 加入/移出工坊                | 企划详情、企划列表、工坊列表、相关广场读取                                |
| 条目创建/删除/发布           | 当前企划条目列表、企划详情及进度相关列表                                  |
| 任务领取/放弃/提交/打回/重置 | 当前条目流程、实例列表、受影响详情、条目进度、企划详情、相关广场/工坊列表 |
| 用户资料修改、加入组织       | 当前用户、组织列表和相关组织信息                                          |
| 组织设置修改                 | 组织信息、账号组织列表中对应展示数据                                      |
| 成员角色/状态、申请审核      | 成员列表、申请列表、相关成员统计；涉及自身权限时刷新身份/角色上下文       |
| 企划类型变更                 | 组织类型列表、用户端类型选项及相关筛选读取                                |
| 管理员/组织管理操作          | 对应系统管理列表和已缓存相关资源                                          |
| 定时任务触发                 | 定时任务列表                                                              |

实现完成时补充每个实际 Mutation 的精确映射；仅失效受影响作用域，不用全站 invalidateQueries 替代映射。

## 8. 错误、重试与取消

- 保留现有 ApiError、GatewayError、AuthExpiredError 语义和业务提示。
- 读取仅对临时网络失败、HTTP 408、429 和 5xx 最多重试 1 次；首次网络故障类型需能与普通业务 ApiError 区分。429 按可用 Retry-After 等待，无该信息时使用有限退避。
- 其他 HTTP 4xx、业务拒绝、登录过期和取消不重试。
- `request.ts` 接受并传递 AbortSignal；AbortError 原样保留，不转换为“网络错误”、不展示提示、不重试。
- 每个 Query 的最终失败最多提示一次；多个订阅组件和中间重试不产生多个 Toast。
- 初次读取失败提供错误与重试入口；后台失败保留数据并提示刷新失败；Mutation 失败保留用户输入。
- 明确现有全局错误通知的来源，再选择唯一提示入口；禁止 request、QueryCache 和页面对同一异常重复提示。
- 未登录登录失败不能当作已登录会话过期跳转，旧会话响应不能清除新会话。

## 9. 本地状态与兼容边界

保留筛选输入、分页选择、弹窗、表单、画板未保存节点、选中节点、文件进度、裁剪状态和必要状态机。服务端状态只保留一份，编辑草稿可以从服务端数据初始化一次。

后台刷新不得重复 reset 表单或覆盖脏字段；资源身份改变时显式切换草稿，遵守现有离开/确认行为。服务端操作成功后才清空草稿，失败保留。现有工作流状态机若保留，只负责交互和提交编排，不另存一份权威服务端快照。

上传资源申请由 Mutation 管理，存储上传继续使用传输层，保留现有上传顺序、错误、取消和完成语义；不能直接用申请完成的 isPending 代表整次文件上传结束。

不新增接口、假数据、后端能力、UI 重设计、任意连线工作流、SSR 或新的全局本地状态库。

## 12. 实施顺序

1. 清点实际调用点，建立 key、错误通知和失效映射，记录当前基线。
2. 接入 QueryClient、身份上下文、取消和重试策略。
3. 迁移当前用户、组织列表和公共选项，删除双重缓存。
4. 迁移企划、工坊、模板、条目、工作流实例及联动失效。
5. 迁移组织管理、系统管理、账号操作和上传资源申请。
6. 扫描遗留请求状态，执行自动检查与真实页面验收，补齐交付记录。

各模块可逐步提交和验证，最终在同一个分支完成全量范围；规格编写阶段没有修改业务代码；后续实施已按本规格推进。
